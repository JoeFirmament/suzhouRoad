# 本地向量库 → 九园剧本、场景与纹样：制作流程

> 2026-10-04。每次设计新章节、新院落、新任务或修改花窗/铺地/匾额之前执行。本规范是**项目内文档**，不把 RAG 回答视为史料。配套设计见 `../姑苏九园-纹样线索与实景图案制作标准.md`。

## 0. 可用入口与边界

- 本地文字集合：`SuzhouClassicGardenRag/Project/data/qdrant` 中的 `garden_knowledge`。原始转换资料在 `SuzhouClassicGardenRag/Project/converted/`。
- 本地图片集合 `garden_images` 存在，但 `config.yaml` 的 `image.enabled: false`；当前 API 只有 `/api/chat`，**没有图片列表或图像检索端点**。图片可从检索到的 Markdown 图版路径回查；若用 `./run.sh query-image`，须另备本地照片/模型，并人工核图注，不能把相似度当身份确认。
- `./run.sh query` 默认还会调用 DeepSeek；**离线/保密制作优先使用 `./run.sh api` 的无 Key 原文检索降级模式**，不得把未公开剧本或本地路径无意发送到外部模型。API 若已运行，不再开另一个读写同一 Qdrant 目录的进程；优先复用已运行的 API。
- 若模型/API 尚不可用，可以对 `converted/` 做 `rg` 定位原文和图版，但在制作卡注明“本次为源文检索，非向量召回”；不伪称问过向量库。
- 本项目已有无需 HTTP 服务、无外部 LLM 的只读入口：`Game/tools/query_garden_rag.py`。它调用现有 BGE/Qdrant 检索器，输出来源、分数和原文片段；不建索引、不写游戏数据。

## 1. 每次先“问三个问题”，再决定设计

围绕**园林 + 具体院落 + 行为**检索，而不是问“有什么好玩的谜题”：

1. **场景**：此处真实的门、墙、廊、水、建筑如何相连？哪个方向可见什么、可走到哪里？
2. **物件**：花窗、铺地、匾额的图案、构图、材质、数量、照片或图版号是什么？图注是否写明具体部位？
   铺地还须区别石板、弹石／弹街石、砖街、卵石和花街等材料与工艺；同名纹样可跨园，具体图案实例和原位不能跨园或跨院挪用。花街铺地可作局部取景、找线索或路径节奏，但不能在未核位时直接覆盖整张可玩底图。
3. **时段**：该物件与本章所选“清末苏州”时段是否同时存在？哪些是后世修缮/复原/游记回忆？

先拿回来源列表，再去原 Markdown/图版/官方实景逐项核。向量匹配分数只代表召回相似，不代表事实可信度。至少再做一次“反向问题”：**有什么资料与我的设想相矛盾？** 人物动机与小游戏解法只在这个边界内写。

### 本机操作例（在仓库根目录）

```bash
conda run -n MinerU python Game/tools/query_garden_rag.py '留园石林小院洞天一碧八角窗六角窗芭蕉竹'
```

这条离线命令优先用于剧本制作；若需要前端/API 交互且本机允许绑定端口，再运行：

```bash
cd SuzhouClassicGardenRag/Project
./run.sh api --port=8000
```

在另一个终端检查 `/api/health`，再向 `POST /api/chat` 发送 `{"query":"留园鹤所、石林小院的方门、空窗和花窗怎样相套？来源与图版号是什么？"}`。未配置 DeepSeek Key 时应看到 `mode: retrieval_only`：读原文片段和 `sources`，不把它当最终答案。若配置了 Key，则 `mode: llm` 是综合叙述，仍须以原文和图版为准。命令行 `./run.sh query "..."` 只在明确允许调用外部 DeepSeek 时使用。

继续问：`留园冰裂纹铺地的书中照片能定位到哪座院落？`、`鹤所门窗在清末是否已有同样布局？`。若回答没有拍摄点/年代，就登记未知，**不得用似是而非的答案补齐**。图像是扫描书籍时还要审使用权。

## 2. 从召回结果到项目产物

| 阶段 | 制作人要留的证据 | 允许做什么 | 禁止做什么 |
|---|---|---|---|
| 召回 | 查询词、时间、集合/模式、命中源文件 | 生成候选清单 | 凭一个 RAG 答案写史实台词 |
| 原件核查 | 书名、页/图号、原图、上下文、图注的具体位置 | 建 `scene-research-candidates.ts` 待核卡 | 从相邻一行错误 OCR 图注推断图片身份 |
| 空间/年代交叉核 | 有方位的图、官方照片、同期材料；矛盾单列 | 给 `scene-evidence.ts` 定 A/B/C 与红线 | 把现状/民国叙述直接写成清末定景 |
| 剧本转化 | NPC 为什么要玩家看、可走线路、错误反馈、奖励幂等 | 进入章节“遇见—循迹—行动—回响” | 问答卡、九园复用同一谜底、改动已定主线 |
| 美术转化 | 原图授权状态、可辨结构、具体园内实例 ID | 原创像素草图、编辑器候选锚点 | 书页截图/检索缩略图/AI 研究图直接发布 |
| 验收 | `?debug=geometry`、键盘/触屏试走、人物比例、历史审核 | 从候选提升到正式资源 | 因为 `tsc` 通过就宣称可玩或史实准确 |

每个图案实例至少记录：`gardenId`、`site`、`surface`（窗/地/额）、`motifFamily`、`instanceId`、`orientation`、`sourceMd`、`figureOrPage`、`periodStatus`、`rightsStatus`、`sceneId`、`scriptRef`、`gameplayRole`、`reviewer`。家族可跨园，例如冰裂、海棠；实例不跨园、不跨场景偷换。

## 3. 复用在剧情中的方式

不是“查到图案 → NPC 讲解图案”，而是：

```text
NPC 的现实需求（借书/寻路/送物/对句）
  → 玩家从库中核过的实物得到可见线索
  → 对照相似纹样的不同实例、视角或铺地/匾额关系
  → 自己走、看、回头、试错
  → 记入园谱的具体实例；史实与创作分层写明
```

当前落实：CH3-06 留园“窗里还有一窗”是未接试玩的候选；书中图 2-5/2-6、5-20～5-22 的窗/芭蕉层次可激发绕行，留园冰裂纹图 1-22 **没有原位定位**，不能先作为石林小院正确答案。九园差异化入口见配套标准 §3。耦园鹤寿亭成对但有差别的窗、退思园九曲回廊诗窗，有望形成不同操作，不复制留园的解法。

## 5. 交付门槛

每次场景/故事提交附“检索记录 + 可核实的原图/原文定位 + 不确定项 + 实际转化点”。若检索无结果，允许创作人物与道具，但不可制造“古迹原有的图案/匾额/密文”。年代、权利或空间位置任何一项不明，就留在编辑器私有研究候选，不进正式故事资源。
